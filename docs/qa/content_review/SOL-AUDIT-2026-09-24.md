# EO-Analyst repository audit

## 1. Executive summary

- This was a read-only static audit. I did not access excluded files, use the network, start the application or database, or run tests.
- The highest security risks are a cloud-provider override that bypasses `allow_cloud: false`, and fetch connections that are checked against approved IPs only *after* connecting.
- Jobs can be lost or falsely reported as complete after lease expiry, a failed cloud-batch fallback, or errors returned by report and pipeline handlers.
- A fixed three-day ingest cutoff permanently skips entries missed during a longer workstation outage. A blocked or snippet-only first fetch also cannot recover when the same URL later serves a good article.
- The recent report recency fix is present, but API, dedup, sitemap, and some report paths still use mutable fetch or modification times as news dates.
- Grounding and citation checks have gaps in rendered fields; one claims-gate branch restores text it just rejected.
- Both named test failures have identifiable test-design causes: one reads live rows, and the other asserts an obsolete output path.
- No static root cause was established for the observed `claim_failed: the connection is lost`; that requires time-correlated database/pool evidence.

## 3. Root cause of the two known failing tests

1. **Monthly deterministic fallback:** [test_monthly_round5.py:455](C:/Users/cohyo/Documents/EO-analyst/tests/unit/test_monthly_round5.py:455) checks the resulting draft against only fixture `MONTH_ITEMS`. The fallback invokes unmocked `collect_israel_items` ([monthly.py:886](C:/Users/cohyo/Documents/EO-analyst/agent/eoa/report/monthly.py:886)), which can add live items and citation numbers. Mock that collector to return `[]`, or capture the full runtime registry and check against it. This test is genuinely dependent on live database contents.

2. **Weekly contaminated-backup rebuild:** [test_report_round3_d6.py:491](C:/Users/cohyo/Documents/EO-analyst/tests/unit/test_report_round3_d6.py:491) asserts the old direct `reports/weekly_<date>.md` path at lines 522–524. [artifacts.py:9](C:/Users/cohyo/Documents/EO-analyst/agent/eoa/report/artifacts.py:9) now always writes under `reports/versions/<uuid>/`. Assert the returned versioned path, its fresh content, and the unchanged backup. The cited assertion is stale even without live data.

**Observed connection loss:** `claim_failed: the connection is lost` has no verified static root cause. The worker catches a failed claim and retries, while [db.py:17](C:/Users/cohyo/Documents/EO-analyst/agent/eoa/db.py:17) uses a process-wide psycopg pool. Correlate the specific failure timestamp with PostgreSQL and pool logs, or inject a broken pooled connection in a test; the repository alone does not establish why the connection was lost.
