# ADR-007: Three QA-r1 traceability decisions (2026-09-06)

**Status:** accepted (2026-09-06)

## Context

`docs/QA_PROGRAM.md` round r1's requirements-traceability layer (Q7,
`docs/qa/findings_Q7_r1.md`, matrix in `docs/qa/traceability_r1.md`) found 14 requirements
partial/missing against the v1.4 spec, of which 9 had no documented decision explaining the gap.
Three of those nine (Q7-4, Q7-5, Q7-9) are recorded here as deliberate decisions rather than
outstanding work, per the FX2 fix-package assignment in `docs/qa/TRIAGE_r1.md`. This ADR is a
standalone decisions record (not a Windows-native-migration decision like ADR-004) covering
otherwise-unrelated traceability gaps, kept together because they were triaged together.

## Decisions

### Q7-9: `contracts` table not built — merged into `events`/`tenders` instead

**Finding:** the spec's FR-6.1 calls for a dedicated `contracts` table. No such table exists in
any migration (`db/migrations/versions/`); `information_schema` was scanned directly to confirm.

**Decision:** contract awards are represented as `events` rows with
`kind = 'contract_award'` (the enum value has been present since the very first migration,
`db/migrations/versions/0001_core.py`) rather than as rows in a separate `contracts` table.
`agent/eoa/tenders/forecast.py` reads exactly this: `_TRIGGER_EVENT_KINDS = ("contract_award",
"deployment", "launch")`, joining those events back to their triggering item for the
forecast-rationale pipeline. Tender/RFI/RFP-side data (the pre-award half of FR-6.1's intent)
lives in the separate `tenders` table added for the A1 tenders module. This was a reasonable
convergence — one fact type (a contract award is fundamentally an event with an amount/parties/
date, exactly like `m_and_a`/`partnership`/`investment`, the other values already in that enum)
rather than a second, largely-duplicate table with its own dedup/provenance/citation plumbing —
but it was never written down as a decision, only discovered by scanning migrations during QA.
Recorded here so a future reader does not go looking for a `contracts` table that was never built,
nor treat its absence as an unimplemented requirement.

**Consequence:** any future FR-6.1-adjacent work (e.g. contract-value rollups, contract-vs-tender
linkage) should extend `events`/`tenders` and `eoa.tenders.forecast`, not introduce a new table.

### Q7-5: FR-10.3 clarification timeout — 5 minutes is the accepted value; FR-10.1 ambiguity gate remains genuinely open

**Finding:** the spec (FR-10.3) calls for a 30- or 60-minute clarification timeout;
`agent/eoa/notify/ntfy.py::ask_user`'s `timeout_min` parameter defaults to
`settings().notify.clarification_timeout_min`, which is **5** minutes
(`agent/eoa/config.py` line 156, `config/config.yaml`'s `notify.clarification_timeout_min: 5`).
Separately, FR-10.1 calls for an ambiguity check before starting a deep-search investigation;
no such check was found in `agent/eoa/search/deep_search.py` or elsewhere.

**Decision (timeout only):** the user explicitly set the clarification timeout to 5 minutes on
2026-09-04 (recorded in this session's operating context as "ntfy consult with 5-min timeout" —
part of the same 2026-09-04 decision that approved the 36-hour autonomous build). This
supersedes the spec's 30/60-minute figure; `config.yaml`'s `5` is correct as shipped and is not a
bug. FR-10.3 in the traceability matrix should be marked "implemented, value overridden by user
decision 2026-09-04" rather than "partial."

**Not decided (still open):** FR-10.1's pre-investigation ambiguity check has no owner and no
scheduled fix package as of this ADR. It remains a genuine gap — `run_analyze`/`deep_search`
currently launch a ReAct investigation directly off whatever query text triggered it (an item's
`I` keyboard shortcut, a chat "המשך חקירה", etc.) with no step that asks the user to disambiguate
a vague query first. Tracked in `docs/qa/findings_Q7_r1.md` (Q7-5) as still "פתוח חלקית" (partially
open) until a fix package picks it up.

### Q7-4: FR-6.4/FR-9.5 dynamic source reliability — deferred, not built

**Finding:** the spec calls for per-source reliability that adapts from measured accuracy history
(FR-6.4, FR-9.5). What exists is a single static `reliability` field per source
(`sources.reliability`, set at ingestion/config time via `config/sources.yaml` and
`upsert_source()`) with no feedback loop that revises it from outcomes (triage corrections,
analyst feedback, deep-search hit quality, etc.). A `source_reliability` table exists in the
schema (`docs/CONVENTIONS.md`'s core-tables list) but nothing currently writes rolling accuracy
history into it from pipeline outcomes.

**Decision:** defer FR-6.4/FR-9.5 rather than build it now. Building a real dynamic-reliability
signal needs a meaningful volume of labeled outcomes (triage corrections, confirmed vs. false
deep-search hits) to be worth computing at all — the system does not yet have that history at
sufficient scale coming out of the Windows-native migration and the U8/A8/A11/A12 feature wave.
Revisit once `triage_feedback`/`security_log`/deep-search outcome data has accumulated over
several weeks of live operation; until then the static `reliability` field (and its manual
`sources.yaml` values) remains the mechanism, and `source_reliability` stays an unused but
schema-ready table for when this is picked back up. No fix package in `docs/qa/TRIAGE_r1.md`
currently owns this.

## Consequences

- `docs/qa/traceability_r1.md` can mark Q7-9 and the FR-10.3 half of Q7-5 as "documented decision"
  rather than "gap"; the FR-10.1 half of Q7-5 and all of Q7-4 remain open, now with an explicit
  owner-less status instead of an undocumented one.
- No code changes accompany this ADR — it is a documentation-only decision record, per the FX2
  fix package's scope (`docs/qa/TRIAGE_r1.md`: "Q7-5/9/4 החלטות").
